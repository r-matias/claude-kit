# Desenho do claude-kit

Resumo das decisões que sustentam o kit. Instalação e uso estão no [README](../README.md); o comportamento exato de cada peça, em [reference.md](reference.md).

## Versão mínima

**Claude Code ≥ 2.1.295.** É a versão que introduz `onFailure: "block"`, usado nos guardas (`guard-bash`, `guard-files`): sem ele, um guarda cujo script falta, quebra ou estoura o tempo deixa a ação passar. O `plugin.json` não aceita campo de versão mínima do Claude Code (os campos com versão são `version`, do próprio plugin, e `dependencies`, de outros plugins), então a exigência fica neste documento, no README, no `/kit:setup`, que para quando a versão é menor, e no aviso que o `session-context` mostra no início da sessão.

A tabela de recursos dependentes de versão está na seção Requisitos e plataformas do README.

## Princípios

1. **Contexto é o recurso escasso.** O que não precisa estar em todo turno vira skill (carrega sob demanda) ou vai para um subagent (contexto separado).
2. **Verificação fecha o loop.** Um check que devolve passa/falha (build, teste, lint) deixa Claude iterar sozinho; o Stop hook transforma isso em portão.
3. **Explorar, planejar, implementar, commitar.** Plano para mudança multi-arquivo ou incerta; diff de uma frase dispensa plano.
4. **CLAUDE.md é conselho; hooks e permissões são garantia.** Regra que precisa valer sempre vai para hook ou permissão.
5. **Quem escreve não revisa.** Revisores rodam em contexto novo, sem permissão de escrita, e só apontam o que afeta correção ou requisito.
6. **Menos peças, mais focadas.** Cada skill, agent e hook precisa ganhar seu lugar.
7. **Após duas correções falhas, `/clear`.** Sessão nova com prompt melhor vence sessão longa com tentativas erradas.

## Três camadas

| Camada | Onde fica | Conteúdo | Muda por stack? |
| --- | --- | --- | --- |
| Usuário | `~/.claude/settings.json`, criado ou completado (merge aditivo) a partir de `plugins/kit/templates/user-settings.json` | Deny de segredos e de git destrutivo, ask de push, sandbox onde existe, kit ligado em todos os projetos ou só nos que o habilitam | Não |
| Plugin `kit` | Este repositório | Skills de fluxo, subagents, hooks e scripts | Não |
| Adaptador | `.claude/kit.json` (do kit), `.claude/settings.json` (criado ou completado) e `CLAUDE.md` (criado só se faltar) do projeto | Comandos do stack, caminhos protegidos, regras de domínio, LSP, `curl`/`wget` negados com o registry liberado | Sim |

Os hooks e as skills nunca chamam um comando de stack diretamente: leem a chave do `kit.json`. Chave ausente é pulada sem erro.

## Decisões

- **Guardas falham fechado.** Sem `jq`, os guardas saem com 2; com `onFailure: "block"`, também bloqueiam se não conseguirem rodar. Hooks de qualidade e de contexto falham aberto (saem com 0), porque não protegem nada. O `session-context` é a exceção que fala: sem `jq` ou `git`, ou com Claude Code antigo, ele avisa com o comando de correção e aponta o `/kit:setup`, porque sem isso o dev só vê os guardas bloqueando sem saber por quê.
- **Hooks em forma shell.** Todos os hooks usam `"shell": "bash"` e `"command": "bash \"${CLAUDE_PLUGIN_ROOT}/scripts/<script>.sh\""`, sem `args`. A forma exec resolve `command` no PATH, e no Windows sem `Git\bin` no PATH o guarda nem inicia; com `onFailure: "block"`, isso trava todo Bash/Edit/Write. A forma shell roda pelo Git Bash que o Claude Code localiza, sem depender do PATH. A suíte simula o caso chamando o `bash.exe` do Git com um PATH sem nenhum `bash`.
- **PowerShell fora no Windows nativo.** Os guardas só cobrem `Bash` e `Edit|Write|MultiEdit|NotebookEdit`. A ferramenta PowerShell executaria comandos sem passar por eles, então no Windows nativo, onde ela existe, o template de usuário põe `"PowerShell"` (nome puro, que remove a ferramenta do contexto) em `permissions.deny`. Quem precisar dela tira essa linha e fica sem guarda nessa ferramenta.
- **Plano sem revisão humana.** O `/kit:plan` e o `/kit:execute` decidem lacunas técnicas sozinhos e registram em "Decisões" do PLAN.md, com data, origem (`kit` ou `usuário`) e motivo; perguntam só em decisão de produto, escopo fora da SPEC ou decisão cara de reverter (e, no execute, antes de ação irreversível). Na dúvida entre técnica e produto, conta como produto. O plano passa pelo `kit:plan-reviewer` (somente leitura, contexto limpo) antes de ser entregue, no lugar da revisão do usuário. Agent separado do `code-reviewer` porque o objeto é outro: plano contra SPEC, sem diff.
- **Plano de trás para frente.** O PLAN.md começa pelos `must_haves` (truths, artifacts, tests) e pelas `Interfaces` exatas, e as tarefas são derivadas deles, para que cobertura e contrato sejam conferíveis antes de qualquer código. Cada tarefa traz `behavior` (vira teste), `action` com molde `arquivo:linha`, `verify` do `kit.json` e `done`, que é o critério do `[x]`. O formato não cita linguagem nem ferramenta: caminhos, assinaturas e comandos vêm do projeto.
- **Waves e checkpoints.** Tarefas agrupadas por dependência; dentro da wave, as que não dividem arquivo vão para subagents em paralelo. O plano declara o paralelo, mas o execute confere os `files` antes de disparar: interseção vira sequência registrada em Decisões, porque dois subagents no mesmo arquivo sobrescrevem um ao outro. O checkpoint só começa quando todas as tarefas voltaram, re-roda os `verify` da wave, porque uma tarefa posterior pode quebrar a anterior, e revisa o diff da wave com o `code-reviewer`, para que um erro não se espalhe pelas waves seguintes antes da revisão final. A base desse diff é uma árvore git gravada no PLAN.md no início da wave (`wave-base.sh`), não um commit: o execute não commita sem pedido e o index do usuário fica intacto. O checkpoint também é o ponto seguro para `/compact`: o estado fica nas caixas do PLAN.md. A wave final é fixa (revisão de código e de segurança, correção com nova revisão, verificação ponta a ponta, `smoke` opcional), então nenhum plano termina sem revisão independente. Só tarefas, checkpoints e passos da wave final levam caixa, porque os hooks contam caixas para mostrar progresso.
- **Uma mensagem por turno.** O `verify-gate` junta falhas de comandos, `key_parity` e `coupled_changes` de todos os repositórios da sessão numa única mensagem, para Claude corrigir tudo de uma vez.
- **Aviso não é bloqueio.** Acoplamentos do tipo "se mudou X, confira Y" usam `level: "warn"` e chegam como contexto na edição (JSON `additionalContext`, porque stdout puro de PostToolUse não chega ao Claude), escritos como fato e não como ordem.
- **Setup sem config manual.** O template da camada de usuário fica dentro do plugin, porque a instalação só copia `plugins/kit`. O setup cria o `~/.claude/settings.json` com o template quando ele não existe e, quando existe, faz o merge aditivo, sempre após confirmação. No escopo "só nos projetos que o habilitam", troca `enabledPlugins."kit@claude-kit"` para `false` (o `/plugin install` grava `true`): é a única troca de valor que o kit faz, porque a chave é dele e o valor é a resposta do usuário. Dependência que falta entra na confirmação com o comando de instalação. O template só tem o que é seguro em qualquer projeto: `curl`/`wget` em deny ficaram no settings do projeto, onde os domínios do stack são liberados junto.
- **Uma porta de entrada, uma confirmação.** O usuário só precisa do `/kit:init`. Ele junta todas as propostas (máquina, projeto, LSP, instalações) e pergunta uma vez; o relatório final não pede ação: o que o kit consegue fazer ele faz depois do "sim", o que não consegue vira aviso de uma linha, e o que é decisão do usuário vira pergunta dentro da confirmação. `/run-skill-generator` e `/verify` ficaram no README como opcionais, não como próximo passo. A máquina é conferida por `setup.sh status` e, faltando algo, o init executa a própria skill do `/kit:setup` em vez de copiar os passos, para a lógica não divergir. O mapa entra sozinho onde ele paga o custo (mais de 300 arquivos de código ou vários repositórios) e a re-execução vira reparo. `/kit:setup` e `/kit:map` continuam avulsos.
- **Mapa fora do `CLAUDE.md`.** Contexto de arquitetura de projeto grande não cabe em todo turno: cada unidade vira uma rule com `paths:`, carregada só quando o Claude toca a área, e a visão geral fica em `docs/codemap.md`, apontada por `.claude/rules/kit-codemap.md`. A partição é um script, sem LLM, para o número de agents ser previsível e o plano aparecer antes do gasto; o limite de agents (30) é o ponto em que o usuário decide.
- **Mapa com evidência e verificador separado.** Toda afirmação do mapa tem `arquivo:linha` e um agent que não produziu o mapa abre uma amostra; o que ele reprova sai. Mapa errado é pior que nenhum, porque os investigadores partem dele; por isso eles também confiam no código quando divergem.
- **Mapeador sem Bash.** Subagent de plugin não aceita `hooks` nem `permissionMode`, e `tools:` só filtra pelo nome da ferramenta, então um Bash restrito a `git ls-files`, `git log` e `wc` não teria garantia. O `kit:mapper` e o `kit:map-verifier` têm só Read, Grep e Glob: somente leitura, sem rede e sem rodar nada do projeto por construção. Contagem de arquivos e linhas vem do `map-partition.sh`.
- **Agent com Bash lê com Read.** O `investigator`, o `code-reviewer` e o `test-writer` precisam de Bash para git e para os comandos do `kit.json`, mas leitura pelo Bash (`cd <repo>; cat -n a.ts b.ts`) cai em regras `ask` do projeto e vira pedido de aprovação para uma simples leitura. Por isso o prompt de cada um manda ler com Read, buscar com Grep/Glob e deixar o Bash só para git e comandos do `kit.json`, sem `cat`/`head`/`tail`/`sed`/`grep`/`find` nem `cd <repo>;` no início.
- **Mapa gravado sem confirmação.** Diferente do init, o `/kit:map` grava direto, porque só cria e regrava arquivos dele (com o cabeçalho `kit:map`), preserva blocos `<!-- manual -->` e tudo fica no git. O ponteiro para o codemap é uma rule nova sem `paths:` (`.claude/rules/kit-codemap.md`, carregada sempre), não uma linha no `CLAUDE.md`. O `allowed-tools` da skill libera Edit/Write só nesses caminhos (`docs/codemap*.md`, `.claude/rules/map-*.md`, `.claude/rules/kit-codemap*.md` e as mesmas com `**/` para os repositórios filhos). Escrita em `.claude/` continua pedindo confirmação: é caminho protegido do Claude Code, e nenhuma regra de allow nem `acceptEdits` dispensa isso (só `bypassPermissions`). O README orienta liberar a pasta `.claude` na sessão no primeiro prompt.
- **O kit só soma.** Em init, setup, map e reparo, `CLAUDE.md`, `.claude/settings.local.json`, `.mcp.json`, skills, agents, commands, rules e hooks existentes nunca são editados, desativados ou apagados. Os settings (`.claude/settings.json` e `~/.claude/settings.json`) recebem só merge aditivo (`merge-json.sh --apply`): itens novos em arrays e chaves ausentes; nunca remove, nunca troca valor, nunca mexe em `hooks`. Antes de gravar há backup ao lado e o diff aparece na confirmação; conflito fica com o valor do usuário e vira uma linha no relatório. Somar um deny também pode mudar comportamento (deny vence allow e ask): deny que sombrearia uma regra de allow ou ask existente não é acrescentado e aparece como "não aplicado". Motivo: quando o kit só gravava uma sugestão ao lado do settings, o usuário precisava aplicar à mão o que o próprio kit propunha (permissões dos comandos, plugin LSP), e o relatório virava lista de tarefas. Acrescentar com backup e diff é auditável e reversível; trocar ou remover não seria, porque a configuração existente tem razões que o kit não vê. Sobreposição: quando a dona é a peça do projeto, o kit se desliga pelo deny; quando a dona é o kit, a peça do projeto fica e `docs/claude-adoption.md` registra. O teste de aceite do modo adotar confere por hash que skills, agents, hooks, rules, `CLAUDE.md` e `settings.local.json` não mudaram, e com `merge-json.sh --check` que o `settings.json` só ganhou itens.
- **Guarda resolve o caminho como o shell resolveria.** Casar texto não basta: `cd / && rm -rf usr`, `rm -rf $(cat lista)`, `sudo -u root rm -rf /` e `C:\x` passavam por um guarda que olhava só a palavra seguinte ao `rm`. O `guard-bash` acompanha `cd` dentro do comando, pula palavras-chave e prefixos que executam o comando seguinte, trata `$()`, crase e `xargs` como alvo não resolvível e normaliza `..` e barras em bash puro. O `guard-files` faz o mesmo com o caminho do arquivo (relativo, `..`, `//`, symlink, maiúsculas em Windows e macOS, `.env ` e `.env::$DATA` no Windows). Na dúvida, nega: um falso bloqueio custa uma frase ao usuário; um falso liberado pode custar o disco.
- **Erro no guarda bloqueia.** `kit_guard_fail_closed` instala um `trap EXIT` que transforma qualquer saída diferente de 0 e 2 (variável não definida, comando quebrado) em exit 2. Sem isso, um `set -u` que abortasse o script com exit 1 deixaria a chamada passar.
- **Bash 3.2.** O `/bin/bash` do macOS é 3.2 e muita máquina não tem outro. Os scripts não usam arrays associativos, `mapfile`, `${x,,}` nem `realpath`/`readlink -f`, e toda expansão de array é `${a[@]+"${a[@]}"}`, porque no bash < 4.4 com `set -u` um array vazio aborta o script. O `verify-gate` guarda os mapas em arquivos temporários e casa os globs num único `awk`, o que também o deixou rápido com milhares de arquivos não rastreados.
- **Sandbox só quando ele existe.** `failIfUnavailable: true` trava toda chamada de Bash se o sandbox não sobe. No Windows nativo ele não existe; no Linux e no WSL2 depende de `bwrap` e `socat`. O bloco `sandbox` do template só entra no macOS e no Linux/WSL2 com os dois no PATH; nos outros casos o settings fica sem ele, em vez de um sandbox declarado que não sobe. O setup avisa quando o AppArmor do Ubuntu 24.04+ restringe user namespaces.
- **LSP pelo init.** O plugin LSP oficial (`<linguagem>-lsp@claude-plugins-official`) entra no `enabledPlugins` do projeto, não do usuário, porque depende da linguagem. O `setup.sh lsp` detecta pelos manifestos, confere o binário do language server e devolve o comando de instalação, que roda dentro da confirmação única. Linguagem sem plugin oficial não é mencionada.
- **Variáveis em `allowed-tools`, conferidas ao vivo.** A página de skills diz que `${CLAUDE_PLUGIN_ROOT}` e `${CLAUDE_SKILL_DIR}` são substituídos nas regras Bash de `allowed-tools`; a tabela de plugins-reference não lista o campo. O `tests/run-permissions-live-test.sh` confirma, com um plugin mínimo e um controle sem a regra, que `Bash(bash "${CLAUDE_PLUGIN_ROOT}/...")`, `Bash(bash "${CLAUDE_SKILL_DIR}/../../...")` e `Read(${CLAUDE_PLUGIN_ROOT}/**)` liberam sem prompt (Claude Code 2.1.299), e que `Agent(<plugin>:<agent>)` em `permissions.deny` bloqueia o subagent enquanto `Agent(<agent>)` sem o prefixo não. Por isso as skills seguem com `${CLAUDE_PLUGIN_ROOT}` e as regras `Read` ficam: sem elas, ler o template ou outra skill do plugin pede confirmação. Quando o init lê outra skill do kit com Read, o texto vem cru; o init diz qual caminho usar no lugar das variáveis.
- **Fronteira.** Nenhum exemplo, teste ou template cita projeto real: só caminhos fictícios.
